# CF-BI KDA: performance engineering (v2 kernels)

The v1 kernels (`docs/20261102-cfbi-design.md`) were correctness-first. This document describes what was done to make
them fast **without changing a single bit of the results**, what was measured on the way (B300, `sm_103a`), what did
and did not pay off, and what is still open. The numerical contract is untouched: every optimisation below is a
different *schedule* of the same floating-point program.

## 1. How "no bit changed" is enforced

`csrc/cfbi/ref/` holds the v1 kernels verbatim (`cfbi::ref`, only the state indexing was changed for `slot_ids`).
The Python API has a hidden `_impl` argument (`0` = optimised kernels, `3` = the reference row engine + K1/K2) and
`tests/cfbi/test_vs_ref.py` runs cold varlen prefill, warm call chains (head rows through the row engine, K1/K2 tails),
decode from every chunk phase, mode 1, the training forward, many heads and every short length through both and compares
the bf16 outputs, the fp32 outputs before rounding, `E`, the valid open-chunk rows and `pos` bit for bit. The older
suites (`tests/cfbi`, including `CFBI_BIG=1`: 32K-token runs, N=512) run against the optimised kernels too (226 tests).
A negative control (one `fma` replaced by `mul`+`sub` in the row engine) is still caught.

## 3. What changed and why

**Measurements that drove the design** (`benchmarks/micro/`, all on this B300): `mma.sync` m16n8k8 TF32 has a 20.7-cycle
dependent latency and saturates at **0.49 MMA/clk/SM** (needs >= 3 independent accumulator chains per warp and 2 warps
per sub-partition). One `dot3` k-step is 3 MMAs, so the MMA pipe alone bounds prefill at ~2.5K cycles per chunk per
BV=16 K2 CTA and the whole K2 at ~3.2 ms for B64/L8K/H6, K1 at ~1 ms; `cp.async.bulk` moves ~62 B/clk/SM from L2 (but many
small copies are slow: one 256-byte row per copy cost ~32 cycles each); `ex2` runs at 32/clk/SM.

**K2 (serial scan over chunks)** - v1 was 25 us per chunk because every k-step of every `dot3` waited for its own global
load. Now: K1 writes every operand in *mma fragment order* (`WS2_*` in `cfbi_common.cuh`), K2 moves each operand into
shared memory with one `cp.async.bulk` + mbarrier and reads fragments as `LDS.128`/`LDS.64`; E and U are kept in shared
memory as pre-split TF32 hi/lo B-fragments (no ALU work on B in the P1/P2/P3 loops); 8 compute warps run
`P1/U | P2` then `P3/E-update | O` in lock step with two CTA barriers per chunk; each operand buffer is refilled as soon
as its last reader has passed a barrier, so the next chunk streams in behind the current one; a CTA owns 16 value
columns, or 8 when the (sequences x heads x 16) grid fits in one wave of SMs (single short sequences: 341 -> 228 us).
The fp32 E elements live in the registers of the warps that update them (a thread owns the same elements for the whole
scan). Result: 3140 -> 219 us (B1/H6), 27222 -> 6378 us (B64); ~4.6K cycles per chunk and CTA (floor ~2.5K at the MMA
pipe: `ncu`: IPC 1.2, 14 % of the warp time at the two per-chunk barriers).

**K1 (chunk coefficients)** - v1: 45 % of the time in exposed global-load latency inside dependent loops, then A/B
operands rebuilt in every 8-column MMA job. Now: all raw q/k/v/g rows `cp.async`'d up front, `khat`/`qhat` recomputed
as `fmul(x, inv)[*scale]` where used (a pure function of the same operands, so the same bits; saves 64 KiB of shared
memory), A operands (`ks`, `qs`, TF32 hi/lo) built once per sub-block into a double-buffered staging area by helper warps
while the MMA warps run the previous sub-block (two tiles per warp, k and q products sharing the B fragments), the
workspace parts that only depend on prep (GQ, KD, GEND) written by the helper warps in the shadow of the MMA phase,
branch-free element code, vector loads in the substitution chain. 28153 -> 8081 us (B64). `ncu` before the last round:
69K warp-instructions per CTA at IPC 1.2 with HMMA only 4.4 % of them; the remaining time is ALU/LDS dominated, 1 CTA/SM
(239 registers, 209 KiB shared memory).

**Row engine (decode, head rows)** - v1 phases cost 14-21K (Akk/Aqk) and 19-41K (P1/P2) cycles of ~45K per row. Fixes, in
the order they paid off: (1) every load that does not depend on the row's prep is issued at the top of the row (cached
UT/W/U rows of the recursion, previous G2 row, `v`) and E / cache lines are prefetched into L2; (2) fully unrolled K loops
with operand loads in front of the MMAs, **and no divergent branches in the fragment construction** (SASS showed one LDG
pair per `if (mine)` branch, i.e. the "hoisted" loads were serialised again: 14K -> 5.5K cycles for P1/P2); (3) `ks`/`qs`
(and `W`/`GQ`) share one MMA tile in A-row slots `s` and `s^8` - allowed by the contract's hardware premise (a tensor-core
output element does not depend on its tile position or on the other rows; `tests/cfbi/test_mma_probe.py`) and confirmed
bit for bit by `test_vs_ref.py`; it halves the MMAs of those phases; (4) the cross-block part of O is computed together
with the UT/W cross-block products, so after P1 only a subtraction and a short FMA chain remain; (5) `__launch_bounds__
(256, 2)` (164 -> <=128 registers, 2 CTAs/SM; 3 or 4 were slower: spills); (6) head rows carry the cached-row registers
from one row to the next instead of re-reading what the previous row just stored (head rows 835 -> 413 us for 44 rows);
(7) chunk-end update with shared KD fragments (60K -> 32K cycles; still the longest row, ~16 us once every 64 rows).

**State pool (`slot_ids`)** - `prefill(..., slot_ids=)` / `decode(..., slot_ids=)`: sequence `n` of the call uses pool
slot `slot_ids[n]`, `-1` = padding entry (no tokens, no state access, `out` untouched). Resolved on the device in the
plan kernel, so CUDA-graph replays can change the buffer. `tests/cfbi/test_slot_ids.py`.

## 4. tcgen05 / UMMA: bit-identical, but slower than `mma.sync` everywhere measured (opt-in: `_impl=8`)

**The bit question.** The CF-BI report kept UMMA only for large V tiles and noted that switching the instruction family needs
its own bit check. We ran it (`benchmarks/micro/umma_probe.cu`, log in `bitwise-test/results/umma_probe_b300.log`):
`tcgen05.mma.cta_group::1.kind::tf32` with K=8 per instruction, issued as the contract's three UMMAs per K-step
(SMALL += lo*hi; SMALL += hi*lo; BIG += hi*hi, TMEM accumulators, K ascending, `fadd_rn(BIG, SMALL)` after `tcgen05.ld`) is
**bit-identical** to the `mma.sync` `dot3`: 0 mismatches in 4.4e9 elements (13 in-contract data regimes incl. denormal `lo`,
wide exponents, cancellation, usage-like gates), M in {64, 128} x N in {8..128} x K in {8..128}, 387,504 tile placements
(position / neighbour independence), negative controls (reversed K order, rounded split, missing lo term, swapped SMALL order,
FMA chain) all differ as they must. The later studies agree: the operand-swapped orientation (A' = Bt rows, B' = A rows) and
A-from-TMEM (`TS`) variants are bit-identical as well (0 mismatches in 19.7M elements per accumulator, SS M'=64/128, TS
M'=128, 10 regimes), and padded descriptor strides (LBO 144 / 160) are exact and cost the same ~155 cycles per K-step. Cost
model (M=128, one k-step = 3 UMMAs): 133 / 133 / 144 / 192 cycles for N = 16 / 32 / 64 / 128, i.e. 4.1x the `mma.sync`
throughput at N = 128, but ~133 cycles of latency per k-step against ~41 for an `mma.sync` chain.

**The kernel** (`csrc/cfbi/cfbi_k2_umma.cuh`, `cfbi_tcgen05.cuh`; `_impl=8` = optimised row engine and K1<16> + this K2, never
chosen by default, dropped by `resolve_impl` on anything but sm_100 / 103). One CTA per (64 value columns, sequence, head), 13
warps, 229 KiB of shared memory, 256 TMEM columns, 1 CTA per SM: one thread issues the UMMAs (P1/P2 = [W;GQ] x E^T as 16
k-steps x 3 UMMAs, P3 = KD x U as 8 k-steps), 4 transform warps turn the fp32 fragment-native workspace operands into hi/lo TF32
planes in the UMMA K-major layout through a 4-stage mbarrier ring, 4 epilogue warps (thread = TMEM lane) compute `U = UT - P1`
and `E' = E*GEND + P3` (the `E^T` row of the thread stays in registers), 4 O warps run the unchanged `mma.sync` cross-block
part and FMA chain. Everything outside the UMMAs is the same explicit `fadd` / `fsub` / `fmul` / `ffma` as in the reference.
`tests/cfbi/test_umma_k2.py` compares bf16 out, fp32 out, `E`, the valid cache rows and `pos` with the `mma.sync` K2 and with
the frozen reference, bit for bit: a single long sequence with a tail, cold varlen batches with empty sequences, warm call
chains, head counts 1 / 6 / 33, every short length, the training forward; its negative control (a build that drops the lo*hi
UMMA) changes 8 % of the fp32 outputs.

**It is slower** (K2 busy time in us, same node, `benchmarks/bench_breakdown.py --impl 0` vs `--impl 8`):

| shape | K2 `mma.sync` (default) | K2 UMMA (`_impl=8`) | UMMA / `mma.sync` |
|---|---|---|---|
| B=1, L=8192, H=6 | 219 | 1206 | 5.5x slower |
| B=8, L=8192, H=6 | 915 | 1256 | 1.4x slower |
| B=64, L=8192, H=6 | 6380 | 7294 | 1.14x slower |
| B=1, L=32768, H=32 | 2411 | 4965 | 2.1x slower |

(K1 is the same kernel in both columns: 134 / 940 / 7540 / 2435 us. These are my numbers on a fresh B300 after the merge; the
UMMA agent measured 1291 / 1307 / 7317 / 5177 us against the `mma.sync` K2 it had branched from, 342 / 1025 / 7169 / 2705 us,
i.e. parity at B64 - the current `mma.sync` K2 keeps `E` in registers and picks BV = 8 for small grids, so the gap is wider.)

Where the time goes (agent timeline at B1, per chunk, in cycles: wait for the E planes 1.9K, P1/P2 stream 8.5K, epilogue-1 6.1K,
P3 stream 4.5K, epilogue-2 1.7K; `ncu`: 69 % of the cycles have no eligible warp, SM throughput 21 %): the UMMA stream is issued
by one thread at ~530 cycles per k-step instead of the ideal ~155 (an `mbarrier.try_wait` on an already complete barrier costs
+565..640 cycles, `tcgen05.commit` +200, even a relaxed load +280..350, because barriers and shared accesses in the issue loop
serialise with the UMMA stream; grouping two stages per hand-off took it from 850 to 530); only the two warps that own TMEM
lanes 0..63 do the `U` work in epilogue-1 (~88 cycles per column); fragment-native `UT` reads are 8-way bank conflicted.
Per-SM throughput at saturation matched the earlier `mma.sync` K2 (about 40K SM-cycles per head-chunk each: 2 CTAs x ~20K cycles
per chunk for UMMA against 8 x 5.1K for `mma.sync`); to win, a UMMA CTA would need <= ~10K cycles per chunk, it is at ~23.5K at
B1 and ~20K at B64. A perfect version of this BV=64, shared-memory-operand design would gain at most ~3x (smem traffic ~1.6 MB per
head-chunk).

**A race found while integrating it (fixed).** In a tail chunk of <= 32 rows two or more O warps have no rows and used to arrive
at `BAR_ODONE` at once, i.e. into the phase of the previous chunk; that phase completed while the slowest O warp (sub-block 3)
still read `sU` / `sP2` / the U planes / `sAQ`, which the next chunk's epilogue and Aqk bulk copy then overwrote: wrong bits in
16 rows x 64 columns, only when timing allowed it (it showed up in one pytest ordering, and once in 60 cold-L2 runs). Found by
bisecting the failing test order, root-caused by reading the barrier arithmetic, confirmed by a deterministic reproducer (the
slowest O warp sleeps 20 us: the old arrival order gives 18,432 wrong fp32 outputs, exactly in the sub-blocks predicted from the
tail lengths; the fixed kernel gives 0). The fix makes an idle O warp wait for the previous chunk's phase before it arrives;
`test_idle_o_warps_in_a_tail_chunk_do_not_race_the_previous_chunk` keeps both variants (fixed must match the reference, the old
order must not). It is a reminder that bit-exact tests on a fast pipeline can pass for a long time on a race.

**Next step, if someone wants UMMA to win** (not built): the operand-swapped design the probe shows to be bit-exact: `E` planes
in TMEM as the A operand, the streamed `W|GQ` / `KD` planes as B, BV = 128, one CTA per head, `U` in TMEM; UMMA time ~4.6K cycles
per head-chunk (M=128, N=128, TS: 192 cycles per k-step), shared-memory traffic ~2.4x lower, estimated ceiling ~4x over
`mma.sync`. It needs K=32-slab hand-offs (or a lighter issue loop) and an epilogue spread over all 8 warps; the 80 KiB ring does
not fit next to the 73.7 KiB `E` planes and 36.9 KiB `U` planes of the current design. UMMA also cannot overlap with K1 (229
KiB per CTA).

## 5. Not done / known limits

- K1 is still ALU/LDS bound at 1 CTA/SM (54 % of the B64 prefill); K2 runs at ~2.2x its MMA-pipe floor at B64. At large batch
  the bitwise-aligned prefill is still ~5x slower than `flash_kda.fwd` (three-term TF32 on `mma.sync`: a hard floor of ~4.2 ms at
  B64/H6/L8K).
- Decode: `plan` + `finalize_pos` add ~3 us per call (PDL / fusing them is open); the chunk-end row is ~16 us once every 64 rows.
- Ampere / Ada (sm_80 / 86 / 89): K1 needs 204 KiB of shared memory, the devices have 163 / 99 KiB, so prefill and the training
  forward run the row engine for every row (same program, same bits, 100+ ms per 4K-token prefill). Keep as a correctness
  fallback or write a small-shared-memory K1: open.
- Bit equality is guaranteed within an architecture family (Hopper == Blackwell, Ampere == Ada), not across.
- Conv / projection layers are validated on B300 only (`bi_linear` refuses other architectures unless
  `FLASH_KDA_CFBI_ALLOW_UNVALIDATED_ARCH=1`), and the bit-aligned projection reaches ~20 % of cuBLAS throughput at large M.
- The UMMA K2 is opt-in and slower (section 4); the operand-swapped redesign is not built.
- Not validated: any GPU / driver / compiler outside the NGC pytorch 26.08 image (nvcc 13.4), mixed-architecture hosts, real
  checkpoints, model quality, multi-GPU tensor parallel.

## 6. Side work

**Other architectures** (merged, `docs/20261102-cfbi-design.md` section 7a): the extension now builds for sm_80 ... sm_120
and the launcher chooses the kernels per device (reference kernels below sm_90; the row engine for every row where K1's 204 KiB
of shared memory do not fit: sm_80/86/89). `flash_kda.cfbi.verify_hardware()` replaces the "compute capability >= 10" guard
by an empirical check of the tensor-core premise (0.2-0.3 s, once per device). Measured: the premise holds and every schedule
matrix passes on B300, B200, H100, A100, A10 and L40S; **H100, B200 and B300 produce bit-identical results** on the dumped
workload (31 tensors, CPU-generated inputs), A100/A10/L40S agree among themselves, but Hopper/Blackwell and Ampere/Ada differ in
the last bits of every three-term product (`ex2` / `rcp` / `rsqrt.approx` are identical; of 1.04M outputs 184 bf16 values differ,
0.018 %, at most 9 ulp; 84.7 % of the fp32 outputs before rounding; 30.6 % of the `E` entries). Bit equality is therefore
guaranteed within an architecture family, not across the two families.

**Context parallelism** (`prefill_k1` / `prefill_k2` / `cp_prefill`, `tests/cfbi/test_cp.py`): K1 needs no entry state, so all
ranks run it at once; K2 is chained through the 64 KiB-per-head fp32 `E` of the previous shard. Shards are cut at multiples
of 64 tokens; the result is bit-identical to one prefill call (tested split by split and with a real two-process gloo run).
K2 is the serial part: its total time stays that of the single-rank K2 (0.22 ms per 8K tokens at H6 here), only K1 (about 37 %
of the single-rank time at this shape) is divided by the number of ranks.

**State pool** (`slot_ids`): see section 3.

**Conv and projections** (`flash_kda.cfbi.short_conv`, `bi_linear`, extension `flash_kda_cfbi_conv_C`, own document
`docs/20261103-cfbi-conv-linear.md`): the causal depthwise conv + SiLU on q/k/v is one fixed fp32 program (ascending-tap `fmaf`
chain, SiLU from `ex2` / `rcp`, bf16 round-to-nearest-even, the state holds the last W-1 raw inputs), the projection is one
`mma.sync m16n8k16` bf16 accumulator chain over K ascending (no split-K) whose row `m` does not depend on `M` or on the other
rows. Every comparison covers bf16 out, fp32 before rounding and the state, zero mismatches: the conv equals the contract
emulation (20 cases), one call == every one of 139 cut points == T=1 decode == random cuts == a varlen batch == the training
forward; the linear row is independent of M (1..2048), row offsets, permutation, neighbours incl. NaN/Inf, N and all 5 tile
configurations; the whole chain (projection -> conv -> CF-BI core) for one prefill call equals prefill + decode token by token
(hidden 1024 and 4096, 1000 tokens, varlen batch with lock-step decode, CUDA-graph decode step), with chain-level negative
controls. Controls: cuBLAS is *not* batch invariant (up to 0.78 % of the bf16 outputs differ between M=1 and M=8192 for some
shapes, though not for K=N=2048..4096 on this GPU), and with cuBLAS projections the chain differs in 3,044 values of `g` and
1,481 core outputs. Speed (B300, K=N=4096, us, `bi_linear` / cuBLAS): M=1 12.1 / 9.1, M=16 12.2 / 11.4, M=64 20.3 / 9.4,
M=128 29.6 / 9.5, M=8192 732 / 154 (376 vs 1784 TFLOP/s: the price of a fixed K order without split-K on `mma.sync` only; the
UMMA family would be the natural way to close it); conv D=4096: decode N=1 / 16 / 64 / 128 2.2 / 2.9 / 3.8 / 6.0 us (FLA's
Triton step kernel 1.5 / 1.7 / 3.3 / 5.4), prefill of 8192 tokens 45.6 us (FLA 42.3, `torch` conv1d 468). Side observation: FLA's
own full-call conv kernel equals `short_conv` on 2.1M outputs, but its own step kernel differs from its own full call in 1 (bf16
weight) / 85 (fp32 weight) outputs. Not covered: other GPUs (premise probes must be rerun), tensor parallel, the gated RMSNorm,
bf16 on UMMA; the backward of both layers is plain torch and not bit-pinned.

**Robustness tests added**: NaN-filled workspace / row cache (`test_stale_memory.py`), NaN / Inf / extreme inputs
(`test_special_values.py`: the optimised kernels propagate them exactly like the reference), guard zones around every
buffer (`test_guard_zones.py`), the `setup.py` build and the JIT build give the same digest.

## 7. K2 from a schedule built on the device (`_impl` bit 4), and the default routing (bit 5)

**The problem.** K2 is a serial scan over the chunks of one (sequence, head, value slice). One CTA fills an SM, so the kernel lasts as long as its busiest SM, and two
things decide that: the order in which the CTAs start (a long item that starts late ends the kernel late) and the width of the value tile of each (sequence, head) pair
(8, 16 or 32 columns: 16, 8 or 4 CTAs per pair; a CTA needs about 3.4 / 4.7 / 7.8 K cycles per 64-token chunk, so wide tiles cost less per column and give fewer, longer
CTAs). The fixed-length launcher picks the width in closed form from `(N * H, SMs)`. The variable-length launcher has to pick it without seeing the lengths: the host never
reads `cu_seqlens` (no synchronisation, CUDA graphs stay legal), so it used one rule from `N * H` alone (8 columns when `N * H * 16` CTAs fit one wave of SMs, else 16) and the
natural grid order, pair by pair. With a skewed batch the longest sequence then starts late, or sits on a narrow tile, while other SMs idle.

**What it does.** With bit 4 set (`_impl=16`) a one-CTA builder kernel `k2_sched_kernel` reads the plan that the first kernels already write (the chunk count of
every sequence, on the device), chooses the widths and the order, and writes one packed int per item (pair, value slice, width) into the plan buffer behind the
`SeqPlan` entries (`workspace_sizes` reports the size). `k2_dyn_kernel` is an ordinary 1-D grid of `16 * N * H` CTAs (the upper bound; the table beyond the item
count holds a sentinel and those CTAs return before they touch anything): CTA `b` reads item `b` and calls the unchanged `k2_tile<8|16|32>`. The arithmetic does not
change: every (pair, value slice) is still exactly one CTA, chunk by chunk, with the same instructions on the same operands, and items share no state (an item owns a
disjoint value slice of one pair: `E` is read and written back only for that slice, the output columns are the slice's, and every shared-memory plane is rewritten
from `E` and the workspace at the start of a tile), so any order and any mixture of widths gives the same bits. `tests/cfbi/test_k2_dyn.py` compares `_impl=16` with
the frozen reference kernels (`_impl=3`) bit for bit on the bf16 and fp32 outputs, `E`, the open-chunk rows and `pos`, for cold and warm chains, split K1 / K2 calls,
context-parallel shards and CUDA-graph replays with rewritten `cu_seqlens`; `test_k2_dyn_variants.py` shows that the harness can fail (separate builds with a skipped
item, an item replaced by its neighbour, a CTA that reads the wrong slice of the K1 output, or no range check for the CTAs beyond the item count: each is caught) and
that the result does not depend on the order or the timing of the CTAs (the CTAs take the items in a permuted order and linger for 2 and 20 us: every bit stays
identical). When all `N * H * 16` CTAs fit one wave of SMs there is nothing to order or choose: the kernel decodes the old schedule itself and no builder runs.

**The policy** (`tests/cfbi/k2_policy.py` is the specification, in integer arithmetic; the builder implements the same, and `test_k2_sched.py` compares the two on every list
of the corpus and checks the invariants of the table on hand-built and random lists). Sequences are sorted by chunk count, longest first. The reference schedule is that
sorted order at the widths of the old launcher. The candidates are every pair at 8, 16 or 32 columns and the mixed ones: the first `x` pairs of the sorted list at one width
and the rest at another, `x` on a grid of 1/16 of the pairs. Every schedule gets an upper bound from list scheduling on `S` SMs under the cost model above, and a pigeonhole
lower bound. With more than three waves of items the bounds are tight: a candidate replaces the reference if its upper bound is at least 3 % below the reference's, and the
reference replaces the old (natural) order if its upper bound is 3 % below the Graham bound of the old order. With fewer waves the bounds are loose, so a candidate must be
certified (its upper bound must not exceed the reference's lower bound) and sorting alone must win by 10 %. Equal lengths use the closed form of the fixed-length launcher.
A fixed-length call can have unequal chunk counts as well (sequences that start inside an open chunk, skipped slots): it gets the schedule of the old launcher exactly,
the closed form over all `N * H` pair positions in natural order (the pairs below `x32` at 32 columns, the pairs without a chunk absent), because the candidates above
are for variable-length calls and the old grid is what a fixed-length call must not lose to (`test_k2_sched.py` reads the table back for warm calls with skipped,
non-contiguous slots).
The constants are those measured on B200 and B300; Hopper uses them unchanged.

**Results.** Medians of five interleaved A/B pairs of processes (each record: 2 repeats of 15 profiled calls; a cell whose spread between the repeats exceeded 0.3 %
was measured again with 45 calls), final tree, B200 and B300 (148 SMs each; B300 is `sm_103a`). The K2 stage is the K2 kernel plus, where it runs, the schedule
builder: what a caller pays. The H100 rows below were measured on an earlier tree of this work, before the two changes described in the next paragraph (the host-side routing rule, off on

**Default routing.** The host does not see the lengths, but it knows `N`, `H`, the number of tokens and the SM count, and the builder is not free: median of the
profiled `k2_sched_kernel` on B200 over the lists measured, 5 us for 2 - 4 sequences, 6 - 9 us up to 16, 8 - 15 us for 24 - 128, 15 us for 256, 26 - 29 us for 512
and 68 us for 1024 sequences. A call with `_impl=0` (the default), a `cu_seqlens`, no forced tile width and mode 0 therefore runs the device-scheduled K2 on a
Blackwell device (compute capability 10, where the cost model was measured) only when it is predicted to gain on any batch of its size. The prediction takes the
worst case of the device policy, equal-length sequences (skew only helps), for which the policy is the closed form of the fixed-length launcher, and compares the two
grids with the cost model of section 3:

- up to one wave of SMs at 8 columns (`N * H * 16 <= SMs`) there is nothing to order or choose: the kernel decodes the old schedule itself and no builder runs; -
  fewer than 256 tokens per sequence (four chunks): a CTA with so little work does not repay the table read, whatever the model says (`64 * 64 @ 6` lost 8.8 %); -
  the closed form must pick another grid than the old rule's 16-column tiles: between one and two waves it does not, and there the table-driven kernel is 2 - 7 %
  slower than the old kernel on the same grid (the K2 stage of `1 * 8192 @ 10` is 5 % longer, `3 * 1536 @ 6` 13 %); - the saving `(co - cd) / co` of the chosen grid
  on the estimated old K2 stage (`co` and `cd` the costs of the old and of the chosen grid per chunk, the stage about `co` times 52.6 ns per chunk of the sequence
  plus 5 us per round of CTAs; the estimate reproduces the measured old K2 stage of equal-length lists with at least four chunks per sequence within a few percent)
  must exceed the builder (an upper envelope of its measured time, by `N` and by `N * H`) and 8 % of the stage (the table-driven kernel is 2 - 5 % slower on the same
  grid, and the model is off by about 3 points). 48 pairs, for example, save 11 % on equal lengths: `8 * 512 @ 6` loses 2 %, `8 * 2048 @ 6` gains 5.6 %; - `N` is at
  most 512: the builder takes up to `min(1024, 16896 / H)` sequences, but at 1024 it needs 68 us and `1024 * 256 @ 1` loses (+1.0 % on B200, +0.3 % on B300 when
  routed).

whose plan buffer was sized by the caller for the old kernels (`SeqPlan` entries only; `workspace_sizes` reports the larger size). `_impl=32` (bit 5) keeps the old

 **Limits and what is not validated.** The builder serves calls of up to `min(1024, 16896 / H)` sequences (the item table is `16 * N * H` ints in the plan buffer);
larger calls run the old kernels, and so do calls with `_impl` bits that exclude it; the default routing stops at 512 sequences. Distinct `slot_ids` and a monotonic
`cu_seqlens` were preconditions of the old kernels and stay unchecked (checking them needs a device synchronisation); the builder trusts the plan, so a non-monotonic
`cu_seqlens` gives a garbage schedule where the old path gave garbage output. The cost-model constants are measured on B200 and B300; on Hopper they are used
unchanged and the default routing is off.

**What not to redo.**

- `initcheck` reports the unwritten 17th float of every Aqk diagonal row (K2 moves the operand with one bulk copy of 2624 floats; K1 writes 16 of the 17 floats of a
  row): harmless, in every K2 kernel, the old ones included, and visible only when the workspace is fresh memory. The sanitizer test therefore hands its calls a
  zero-filled workspace and fresh, never written plan buffers, so a report that remains is a finding of the new path; with that, `memcheck`, `synccheck`, `racecheck`
  and `initcheck` all report nothing over a whole device-scheduled prefill (the test takes about 95 s; with the unwritten pad floats `initcheck` printed 470,016
  lines and needed 30 minutes). - A `_impl=0` comparison in a test or a benchmark no longer measures the old kernels once the default routes: use `_impl=32` for the
  old kernels and check which kernels launched (`launched()` / `require_dyn` / `require_old` in `test_k2_dyn.py`), or the comparison is vacuous. - The whole-call
  time of a list whose sequence lengths are not multiples of 64 is dominated by the row-engine kernel (`rows_kernel`: hundreds of us, with a range of 25 - 75 %
  between repeats): compare the K2 stage, not the total, for such lists (`32 * 255 @ 6` showed +46 % in the total with identical K2 kernels). - The model-based
  routing rule was tuned on lists whose sequences are equal, skewed or random but all multiples of 64 tokens and all with 6 - 40 heads or fewer; before changing its
  constants, measure a fresh held-out set again (`tests/cfbi/test_k2_policy.py` lists the 40 that were used).
