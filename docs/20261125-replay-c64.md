# Chunk-64 bf16 KDA with a bitwise-aligned decode (`flash_kda.replay64`)

*2026-11-25, branch `feature/kda-replay-decode`*

## 1. What this adds

The chunk-16 work on this branch (`docs/20261124-replay-decode.md`) makes decode reproduce the unmodified
`flash_kda.fwd` bit for bit. This document adds the **chunk-64** counterpart:

* `flash_kda.replay64.fwd64`: a new prefill kernel pair (K1 + K2) with a 64-token chunk, written in the style of
  `flash_kda.fwd` (bf16 intermediates, bf16 `mma.sync` with fp32 accumulate, bf16 state rounded once per chunk end);
* `flash_kda.replay64.prefill` / `decode` / `final_state`: serving entry points whose outputs are bit-for-bit equal to ONE
  `fwd64` call over the whole sequence, however the sequence is cut into calls (the chunk-16 contract, with 64).

There is no chunk-64 original to keep unmodified (`flash_kda.fwd` is `CHUNK = 16` throughout, and its exponentials only
stay in range for 16 rows: `|lower_bound| * 16 * log2(e) < 128`), so `fwd64` is new code, and decode and prefill share
the same device functions instead of a generated copy.

Files: `csrc/c64/` (separate extension `flash_kda_C64`, raw CUDA, no CUTLASS), `flash_kda/replay64.py`,
`tests/test_replay64.py`, `tests/c64_helpers.py`, `benchmarks/{c64_bringup,bench_c64,prof_c64,prof_phases_c64,probe_mma_rate}.py`.

## 2. The chunk-64 program

Per head, K = V = 128, chunk of 64 rows anchored at the sequence start, split into four 16-row sub-blocks b with the
reference cumsum R_b = G[16b - 1] (R_0 = 0). G is the gate cumsum (log2 domain, a sequential fp32 fold over the rows).

| quantity | definition (bf16() = round to nearest even) |
|---|---|
| khat, qhat | bf16(x * rsqrt(sum x^2 + 1e-6)) (as flash_kda.fwd) |
| a2, G | a2 = lower_bound * log2(e) * sigmoid(exp(A_log) (g + dt_bias)), G = sequential fp32 cumsum |
| kd_loc_i, qd_loc_i | bf16(khat * bf16(ex2(G - R_i))), bf16(bf16(qhat * bf16(ex2(G - R_i))) * bf16(scale)), rows of sub-block i |
| w_ij (j <= i) | bf16(khat_j * bf16(ex2(R_i - G_j))) |
| L_ij, Mqk_ij | L = sigmoid(beta_i) * (kd_loc_i . w_ij^T) (fp32, strictly lower), Mqk = bf16(qd_loc_i . w_ij^T) (lower incl. diagonal) |
| INV = (I + L)^-1 | 16x16 diagonal blocks: 8x8 fp32 forward substitution + bf16 merge (the routine of `csrc/smxx/utils.cuh`); off-diagonal blocks INV_ij = -INV_ii . bf16(sum_m bf16(L_im) INV_mj), m ascending |
| Kd, Qd, Kr | bf16(khat * bf16(ex2(G))), bf16(bf16(qhat * bf16(ex2(G))) * bf16(scale)), bf16(khat * bf16(ex2(G_end - G))) |
| recurrence | P = bf16(Kd S^T), O0 = bf16(Qd S^T), W' = bf16(bf16(v - P) * bf16(sigmoid beta)), U = bf16(INV W'), out = bf16(O0 + bf16(Mqk U)), S' = bf16(fma(S, ex2(G_end), Kr^T U)) |

Every exponential factor is <= 1 except the in-sub-block ones (<= 2^127 for |lower_bound| <= 5.5), the same range as
chunk 16. Products are `mma.sync.m16n8k16` bf16 with fp32 accumulate, K ascending in steps of 16; elementwise bf16 math
uses `mul/sub/add.rn.bf16x2`; every fp32 operation is an explicit intrinsic and the extension is built with
`-fmad=false`.

**Accuracy** (relative RMS against the fp64 recurrence, in units of the bf16 rounding floor; `tests/c64_helpers`
regimes, T = 1024, H = 4, B300): authors 3.06, unit 3.40, heavy_tail 3.18, long_memory 3.82, no_decay 3.80,
eps_dominated 3.28, saturated 2.92, one_hot 2.96. A CPU emulation of both programs (same rounding points) puts
`flash_kda.fwd` at 3.17 / 3.44 / 3.70 / 4.71 / 4.71 / 3.32 / 2.97 / 2.78 on T = 2048 and reproduces its measured GPU
values (3.14 / 3.44 / 3.44 / 4.69 / 4.71 / 3.34 / 2.96 / 2.79) within ~8%: the chunk-64 program is as accurate as the
chunk-16 original, better where memory is long (one bf16 state rounding per 64 tokens instead of per 16).

## 3. Why decode can match the prefill, and the state

Inside a chunk, output row r reads rows 0..r of k, v, g, beta, row r of q and the chunk-start state (the cumsum is a
sequential fold; L, Mqk, INV are lower triangular with exact zeros above the diagonal; sub-blocks after r's are never
read). So a decode step for the token at chunk row r runs the chunk arithmetic on rows 0..r of the open chunk and emits
row r; at 64 rows the state update runs and the chunk closes. State per (slot, head): S bf16 [128, 128] (32 KiB) + raw
k, v, g rows [64, 128] (48 KiB) + beta [64] + pos = 80 KiB (chunk 16: 44 KiB).

## 4. Kernels

* **K1** (`c64_k1.cuh`, 256 threads, 108 KiB smem, 2 CTAs/SM): gate + cumsum (threads 0-127) next to the l2norm
  (threads 128-255); the 10 sub-block pairs (i, j <= i), one warp each, fragments built on the fly; diagonal inverses
  (warps 0-3) and three levels of block forward substitution; Kd / Qd / Kr written through a sink.
* **K2** (`c64_k2.cuh`): one 64-row step from S; the recurrence is independent per value column, so the 128 columns
  may be split over 1, 2 or 4 CTAs per (sequence, head) (`_auto_k2_cfg`: <= 16 chains -> 4 CTAs of 2 warps, <= 64 ->
  2 CTAs of 4 warps, else 1 CTA of 8 warps). Every split gives the same bits (tested).
* **replay** (`c64_replay.cu`, 256 threads, 161 KiB smem): stages the open chunk (cp.async), runs `k1_core` and
  `k2_step` (the same functions), emits the new rows, closes the chunk when it reaches 64 rows; `final_state` uses a
  peek mode (close a short chunk into a separate buffer).
* **prefill flow** (`replay64.prefill`): rows that complete an open chunk -> replay; the 64-aligned bodies -> ONE
  `fwd64` launch over a segment table (no pseudo-sequences); the tail -> replay.

## 5. Verification

`tests/test_replay64.py` (GPU, 150 cases, 1.9 s of GPU time on a B300; every comparison on raw bits, output buffers
pre-filled with NaN): premises on `fwd64` (row t of a call == row t of the call over 0..t around every chunk boundary,
split at 64-multiples == one call incl. fp32 initial state, the open-chunk oracle, empty sequences incl. separate
final-state buffers, the four K2 CTA shapes identical); decode from an empty state (6 gate regimes x H 1/4, big v,
collinear keys, extreme beta / gates, the 8 data regimes); prompt L in {1, 5, 63, 64, 65, 127, 128, 129, 300, 1000} x
initial state {none, bf16, fp32} + 70 decode steps with `final_state`; multi-token decode steps (2..70 tokens, closing two
chunks in one call); slot pools with padding entries (padding rows and unnamed slots untouched); random chunked-prefill
cuts; both prefill paths and both planners (device / host, batched / varlen, with and without slot pools); continuation
calls mixing heads / bodies / tails / 0-token sequences, `cu_seqlens[0] != 0`; `final_state` with slot pools at pos 0 and
mid-chunk (state unchanged); H = 1 / 32 / 96; captured CUDA graphs (also with a rotating slot mapping); determinism;
accuracy against the fp64 recurrence. The chunk-16 suites (`tests/test_replay.py`, `tests/test_replay_codegen.py`) still
pass on the same build (238 tests in total).

The tests found one gap that was fixed: with separate initial / final state buffers, an empty sequence did not get its
initial state copied into the final state (`flash_kda.fwd` does that). `compute-sanitizer` (memcheck, racecheck,
synccheck) is clean on fwd64 (all four K2 CTA shapes) and on the replay kernel; racecheck found one real hazard that was
fixed (the replay kernel copied the new raw rows into the row cache without a barrier before K1's in-place l2norm).
`benchmarks/c64_golden.py` confirmed that neither fix nor any of the performance changes moved a bit.

Development checks: `benchmarks/c64_bringup.py` (accuracy on 8 regimes, replay == fwd64 over ~40 cut points, K2 shapes
identical, host plan == device plan == fwd64) and `benchmarks/c64_golden.py` (bit-for-bit regression of fwd64 and decode
outputs across rebuilds that must not change numerics).

Within chunk 64, prefill geomeans relative to fwd64: CF-BI C64 1.90x, Inferact v5 2.24x, FLA 1.46x. Against the
chunk-16 original, fwd64 is faster on single long sequences (1 x 196608: 0.59x of `flash_kda.fwd`; 1 x 4096: 0.64x) and
slower on equal-length batches (8 x 8192 1.11x, 64 x 512 1.50x, 24 x 8192 1.50x): K2 needs 4x fewer serial steps and its
128 value columns can be split over 1-4 CTAs, while K1 computes ten 16x16 sub-block pairs per 64 rows instead of four.
Decode replays up to 64 rows per step (chunk 16: up to 16) and reads 80 KiB of state per (sequence, head); it is
1.8-2.6x slower than the chunk-16 replay.

Kernel-level notes (clock64 per phase, `benchmarks/prof_phases_c64.py`): a K2 step (64 rows) takes ~5.9 K cycles with
2 warps x 16 columns per CTA; one K1 tile ~25 K cycles, its sub-block pair phase is bound by MUFU (ex2) and
shared-memory throughput. `mma.sync` m16n8k16 bf16 on the B300 peaks at 2 SM-cycles per instruction with >= 4 warps
(`benchmarks/probe_mma_rate.py`).

## 7. Scope and limits

* Same build, same GPU architecture (sm_103a measured); finite inputs; `lower_bound >= -5.5`.
* The chunk-64 program is a new numerical contract: bitwise equal to itself (prefill / decode / any cut), not to
  `flash_kda.fwd`, `flash_kda.cfbi`, FLA or the recurrent kernels.
* Training forward / backward alignment is not covered (as for chunk 16).
